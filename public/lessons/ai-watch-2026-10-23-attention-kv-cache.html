Attention and the KV cache: why a long conversation costs memory

A model rereads everything you wrote before it writes each new word. The trick that keeps this from being impossibly slow is a notebook called the KV cache, and the notebook is why long context, prompt caching and GPU bills are all connected.

1. Attention: a search over everything so far

You know from the tokens and embeddings lessons that text becomes a list of vectors. Attention is the step where each token decides which earlier tokens matter to it. For every token the model computes three vectors from its embedding:

  • Query (Q): what this token is looking for.
  • Key (K): what each earlier token advertises about itself.
  • Value (V): the actual information that token hands over if it is picked.

The current token's Query is compared with every Key. The scores go through softmax (the same function from the temperature lesson) and become weights that add up to 100%. The output is the weighted mix of all the Values. In the formula from the Hugging Face docs: softmax(Q·Kᵀ / √d) · V, with a mask so a token can never look at the future.

Analogy: a library. The Query is your question at the desk. Each Key is the label on a book's spine. The Value is the book's content. You do not read one book: you read a blend of all of them, weighted by how well each label matched your question.

A tiny version in plain JavaScript, for one query against three earlier tokens:

function attention(q, keys, values) {
  // score = how well the query matches each key
  const scores = keys.map(k => k.reduce((s, x, i) => s + x * q[i], 0) / Math.sqrt(q.length));
  const max = Math.max(...scores);
  const exps = scores.map(s => Math.exp(s - max));
  const sum = exps.reduce((a, b) => a + b, 0);
  const weights = exps.map(e => e / sum);         // add up to 1
  // output = weighted mix of the values
  return values[0].map((_, i) => weights.reduce((s, w, j) => s + w * values[j][i], 0));
}

2. The waste: recomputing the past

A model writes one token at a time. To write token 501 it needs the Keys and Values of tokens 1 to 500. Without any shortcut, it would rebuild all 500 of them. For token 502 it would rebuild 501, and so on. Generating N tokens would take roughly N²/2 units of work. For 1,000 tokens that is about 500,000 operations instead of about 1,000.

The key observation: because a token can only look backward, its Key and Value never change once computed. They depend only on that token's own input and the frozen model weights. Recomputing them is pure waste.

3. The KV cache: a notebook of what is already known

The KV cache stores the Keys and Values of every token already processed, in every layer of the model. For a new token, the model computes only that token's Q, K and V, appends the new K and V to the notebook, and runs the lookup. Notice the cache keeps K and V but not Q: an old Query is never needed again.

One generation has two phases, which behave very differently:

PhaseWhat happensWhat limits speed
PrefillThe whole prompt is processed in parallel and the cache is filledRaw compute. This is the wait before the first word appears.
DecodeOne token at a time; each step reads the whole cacheMemory bandwidth. A bigger cache means more data to read per word.

The Hugging Face documentation describes the trade: without the cache, attention work per step grows with the square of the sequence length; with it, work per new token stays low while memory grows linearly. One benchmark in the Morph article (a T4 GPU, 1,000 tokens) measured 11.9 s with the cache versus 56.2 s without, about 4.7x. Treat that as one data point on one GPU, not a universal number. The gap widens with longer output.

The core trade: the KV cache swaps compute for memory. Almost every optimization below is a different way of managing that swap.

4. The bill: memory that grows with every token

The size of the notebook for one conversation is:

bytes = 2 × layers × kv_heads × head_dim × tokens × bytes_per_number
        ↑ K and V

It grows with every token, for every layer, for every simultaneous user. Try it. The presets use the public architectures of Llama 3.1 8B and 70B (32 and 80 layers, 8 KV heads, head size 128), which are commonly cited examples:

–

With 16-bit numbers, the 70B-class model needs about 0.31 MB per token, which is about 40 GiB for a single 128K-token conversation. That is more than the weights of the same model compressed to 4 bits (about 35 GB), per the Morph article. Serve ten users at once and you multiply it by ten. This is why the cache, not the model weights, is often the real ceiling on how many people one GPU can serve.

Using its formula, the 8B model needs about 0.5 / 4 / 16 GiB at 4K / 32K / 128K tokens (the table says 0.13 / 1 / 4), and the 70B needs about 1.25 / 10 / 40 GiB (the table says 0.33 / 2.5 / ~40). I recomputed everything above from the formula. Lesson for the habit: when a table and a formula disagree, run the formula.

5. How the industry shrinks the notebook

  • Grouped Query Attention (GQA): many Query heads share a few KV heads. Llama 3.1 70B has 64 query heads but only 8 KV heads, an 8x smaller cache than giving each query head its own. It is now the default in most open models.
  • Multi-Head Latent Attention (MLA): introduced by DeepSeek-V2, it compresses K and V into a small latent vector before caching. The Morph article reports a 93.3% cache reduction versus standard multi-head attention (a figure from DeepSeek's own paper, via Morph).
  • Quantization: store the cache in FP8 or 4-bit instead of 16-bit. FP8 halves it with small accuracy impact; 4-bit saves about 4x but can lose a little quality at high load.
  • Paged attention (vLLM): instead of reserving one big block per conversation for the maximum length, allocate small blocks on demand, like virtual memory in an operating system. Morph cites memory waste dropping from 60-80% to under 4%, and 2-4x more throughput.
  • Sliding windows: some layers keep only the last N tokens in the cache, so those layers stop growing.

6. What this means for you as a developer

Prompt caching is the KV cache, sold to you

The key for a token depends only on the tokens before it. So if two requests start with the same 5,000 tokens, their caches for that part are identical, and a provider can reuse it instead of recomputing. That is prefix caching, and it is what the prompt caching lesson was about. It explains the practical rule: put stable content first (system prompt, tool definitions, reference documents) and variable content last. Change one token early in the prompt and everything after it misses the cache.

Why long context is not free

A 1M-token window means a 1M-entry notebook per layer. That is why providers add surcharges, limits or slower speeds for very long prompts, and why the context window lesson warned that a bigger window does not solve everything. Fewer input tokens means a faster first word, a smaller memory read per word, and room for more users on the same hardware.

Why agents get slower as sessions grow

A coding agent that has accumulated 50,000 tokens of old tool output pays for that cache on every step. Trimming stale context is not only about staying under the limit: it makes each remaining step cheaper.

A short exercise

Using the formula, estimate the cache for your own case. Take an 8B-class model (32 layers, 8 KV heads, head size 128, 16-bit) serving 20 users at 8K tokens each. Answer: 131,072 bytes per token × 8,192 tokens × 20 users ≈ 21.5 GB, before counting the model weights. Now try halving the precision in the calculator above.

1. Atenção: uma busca em tudo que veio antes

Você viu nas lições de tokens e embeddings que o texto vira uma lista de vetores. A atenção é a etapa em que cada token decide quais tokens anteriores importam para ele. Para cada token, o modelo calcula três vetores a partir do embedding:

  • Query (Q): o que este token está procurando.
  • Key (K): o que cada token anterior anuncia sobre si.
  • Value (V): a informação de fato que esse token entrega se for escolhido.

A Query do token atual é comparada com todas as Keys. As notas passam pelo softmax (a mesma função da lição de temperature) e viram pesos que somam 100%. A saída é a mistura ponderada de todos os Values. Na fórmula da documentação do Hugging Face: softmax(Q·Kᵀ / √d) · V, com uma máscara para o token nunca olhar o futuro.

Analogia: uma biblioteca. A Query é a sua pergunta no balcão. Cada Key é a etiqueta na lombada de um livro. O Value é o conteúdo do livro. Você não lê um livro só: lê uma mistura de todos, ponderada pelo quanto cada etiqueta combinou com a sua pergunta.

Uma versão minúscula em JavaScript puro, para uma query contra três tokens anteriores:

function attention(q, keys, values) {
  // nota = quanto a query combina com cada key
  const scores = keys.map(k => k.reduce((s, x, i) => s + x * q[i], 0) / Math.sqrt(q.length));
  const max = Math.max(...scores);
  const exps = scores.map(s => Math.exp(s - max));
  const sum = exps.reduce((a, b) => a + b, 0);
  const weights = exps.map(e => e / sum);         // somam 1
  // saída = mistura ponderada dos values
  return values[0].map((_, i) => weights.reduce((s, w, j) => s + w * values[j][i], 0));
}

2. O desperdício: recalcular o passado

Um modelo escreve um token por vez. Para escrever o token 501, precisa das Keys e Values dos tokens 1 a 500. Sem nenhum atalho, reconstruiria os 500. Para o 502, reconstruiria 501, e assim por diante. Gerar N tokens custaria cerca de N²/2 unidades de trabalho. Para 1.000 tokens, são uns 500.000 cálculos em vez de uns 1.000.

A observação-chave: como um token só olha para trás, a Key e o Value dele nunca mudam depois de calculados. Dependem só da entrada daquele token e dos pesos congelados do modelo. Recalcular é puro desperdício.

3. O KV cache: um caderno do que já se sabe

O KV cache guarda as Keys e Values de todo token já processado, em todas as camadas do modelo. Para um token novo, o modelo calcula só o Q, K e V dele, acrescenta o novo K e V ao caderno e faz a busca. Repare que o cache guarda K e V, mas não o Q: uma Query antiga nunca é usada de novo.

Uma geração tem duas fases, que se comportam de forma bem diferente:

FaseO que aconteceO que limita a velocidade
PrefillO prompt inteiro é processado em paralelo e o cache é preenchidoPoder de cálculo. É a espera antes da primeira palavra aparecer.
DecodeUm token por vez; cada passo lê o cache inteiroLargura de banda de memória. Cache maior significa mais dados lidos por palavra.

A documentação do Hugging Face descreve a troca: sem cache, o trabalho de atenção por passo cresce com o quadrado do tamanho da sequência; com cache, o trabalho por token novo continua baixo, enquanto a memória cresce de forma linear. Um benchmark do artigo da Morph (GPU T4, 1.000 tokens) mediu 11,9 s com cache contra 56,2 s sem, uns 4,7x. Trate como um dado de uma GPU, não como número universal. A diferença aumenta com saídas mais longas.

A troca central: o KV cache troca cálculo por memória. Quase toda otimização abaixo é uma forma diferente de administrar essa troca.

4. A conta: memória que cresce a cada token

O tamanho do caderno de uma conversa é:

bytes = 2 × camadas × kv_heads × head_dim × tokens × bytes_por_número
        ↑ K e V

Ele cresce a cada token, em cada camada, para cada usuário simultâneo. Teste. Os presets usam as arquiteturas públicas do Llama 3.1 8B e 70B (32 e 80 camadas, 8 KV heads, tamanho de head 128), exemplos muito citados:

Com números de 16 bits, o modelo de classe 70B precisa de cerca de 0,31 MB por token, ou seja, uns 40 GiB para uma única conversa de 128 mil tokens. É mais do que os pesos do mesmo modelo comprimido para 4 bits (uns 35 GB), segundo o artigo da Morph. Atenda dez usuários ao mesmo tempo e multiplique por dez. Por isso o cache, e não os pesos do modelo, costuma ser o teto real de quantas pessoas uma GPU atende.

Atenção: erro numa fonte. A tabela de tamanhos do artigo da Morph é inconsistente com a própria fórmula, exceto na linha do 70B a 128K. Usando a fórmula, o modelo 8B precisa de cerca de 0,5 / 4 / 16 GiB a 4K / 32K / 128K tokens (a tabela diz 0,13 / 1 / 4), e o 70B de cerca de 1,25 / 10 / 40 GiB (a tabela diz 0,33 / 2,5 / ~40). Recalculei tudo acima a partir da fórmula. Lição de hábito: quando tabela e fórmula discordam, rode a fórmula.

5. Como a indústria encolhe o caderno

  • Grouped Query Attention (GQA): várias heads de Query compartilham poucas heads de KV. O Llama 3.1 70B tem 64 heads de query mas só 8 de KV, um cache 8x menor do que dar uma head de KV para cada query. Hoje é o padrão na maioria dos modelos abertos.
  • Multi-Head Latent Attention (MLA): criada no DeepSeek-V2, comprime K e V num vetor latente pequeno antes de guardar. O artigo da Morph relata 93,3% de redução do cache frente à atenção multi-head padrão (número do paper da própria DeepSeek, via Morph).
  • Quantização: guardar o cache em FP8 ou 4 bits em vez de 16 bits. FP8 corta pela metade com pouco impacto de precisão; 4 bits economiza uns 4x, mas pode perder um pouco de qualidade com carga alta.
  • Paged attention (vLLM): em vez de reservar um bloco grande por conversa para o tamanho máximo, aloca blocos pequenos sob demanda, como a memória virtual de um sistema operacional. A Morph cita o desperdício caindo de 60-80% para menos de 4%, e 2-4x mais vazão.
  • Janelas deslizantes: algumas camadas guardam só os últimos N tokens, então essas camadas param de crescer.

6. O que isso significa para você, dev

Prompt caching é o KV cache, vendido para você

A key de um token depende só dos tokens anteriores. Então, se duas requisições começam com os mesmos 5.000 tokens, os caches dessa parte são idênticos, e o provedor pode reaproveitar em vez de recalcular. Isso é o prefix caching, tema da lição de prompt caching. Ele explica a regra prática: coloque o conteúdo estável primeiro (system prompt, definições de ferramentas, documentos de referência) e o variável por último. Mude um token no começo do prompt e tudo depois dele perde o cache.

Por que contexto longo não é de graça

Uma janela de 1M de tokens significa um caderno de 1M de entradas por camada. Por isso provedores colocam sobretaxas, limites ou menos velocidade para prompts muito longos, e por isso a lição de context window avisou que janela maior não resolve tudo. Menos tokens de entrada significa primeira palavra mais rápida, menos memória lida por palavra e espaço para mais usuários no mesmo hardware.

Por que agentes ficam mais lentos conforme a sessão cresce

Um agente de código que acumulou 50 mil tokens de saídas antigas de ferramentas paga por esse cache a cada passo. Podar contexto velho não serve só para ficar abaixo do limite: deixa cada passo restante mais barato.

Usando a fórmula, estime o cache do seu caso. Pegue um modelo de classe 8B (32 camadas, 8 KV heads, head de 128, 16 bits) atendendo 20 usuários com 8K tokens cada. Resposta: 131.072 bytes por token × 8.192 tokens × 20 usuários ≈ 21,5 GB, sem contar os pesos do modelo. Agora tente reduzir a precisão pela metade na calculadora acima.
