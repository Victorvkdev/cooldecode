Six permission modes and a very long variable name: how a coding agent decides when to ask

On October 27, Claude Code shipped an environment variable called CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS. The joke writes itself, but the change is a good excuse to understand the whole permission system of a coding agent: what each mode allows, which checks survive every mode, and why the real safety line is somewhere else.

1. The news: the last prompt you can now turn off

Claude Code has long had a flag, --dangerously-skip-permissions, that starts a session in bypassPermissions mode, where the agent runs tools without asking. The Register reports the mode first appeared in v1.0.18, in June 2025. What fewer people knew: even that mode never approved everything. A short list of actions still stopped for a human, and the most visible one was deleting a "critical path" such as your home directory.

With v2.1.311 (released around October 26–27, 2026), an Anthropic engineer, Daisy Hollman, posted that this last guardrail can now be disabled too, by starting Claude Code with CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1. Readers assumed it was a joke; she replied "Not a joke!". The Register noted that the change was not in the v2.1.311 changelog at the time of its article. The official permission-modes documentation now describes it in detail, with a warning that rm -rf ~ can then run without asking.

Why this is news at all: nothing got more dangerous by default. The change only affects people who already chose the most permissive mode and explicitly set a second, oddly named variable in their shell. The interesting part is what it reveals about how the permission system is built.

2. The six modes, side by side

A permission mode decides which actions the agent can take without asking you first. Claude Code has six. The table below follows the official docs; "Manual" is the name the UI shows for the config value default.

ModeRuns without askingMeant for
default (Manual)Reads onlyReviewing every action, sensitive work
acceptEditsReads, file edits, common filesystem commands (mkdir, touch, mv, cp…)Iterating on code you are reviewing
planReads (plus classifier-approved commands when auto mode is available); edits wait for an approved planExploring before changing anything
autoEverything, with a second model (the classifier) reviewing actions in the backgroundLong tasks, less prompt fatigue
dontAskReads in your working directories and pre-approved tools; anything that would prompt is deniedLocked-down CI and scripts
bypassPermissionsEverythingIsolated containers and VMs only

Two details worth noticing. First, auto is now the built-in starting mode for interactive terminal and VS Code sessions on v2.1.283 or later (it became the default in August, as covered here on Aug 12). Second, dontAsk is the opposite of what its name suggests to some people: it does not "skip asking and do it", it "skips asking and refuses". That makes it the right choice for a CI job, where nobody is around to answer.

3. Modes are only the baseline: four layers

The most common misunderstanding is to treat the mode as the whole story. In practice there are layers, and some of them apply no matter which mode you pick:

1Rules. You can write allow, ask and deny rules per tool, such as Bash(git push *). Deny rules block in every mode, including bypassPermissions. Allow rules, on the other hand, have no effect in bypassPermissions (everything is already allowed).
2The mode. Decides the default answer for whatever no rule covers.
3Things no mode auto-approves. Explicit ask rules, tools that need a human by design (such as a "ask the user a question" tool), connector tools your organization marked as "ask", and recognized rm/rmdir on critical paths. This list is what the new variable shortens.
4Isolation. A sandbox, container or VM limits what an action can reach once it runs. The docs put it plainly: modes decide whether Claude asks; the sandbox and isolation decide what an action can touch.

In auto mode the order is fixed: rules resolve first; then reads and edits inside the working directory are auto-approved; everything else goes to the classifier; if the classifier blocks, the agent receives the reason (often a rule name like [Data Exfiltration]) and has to try something else.

4. Critical paths: the check behind rm -rf ~

Before any rm or rmdir runs, Claude Code inspects the target. It treats as critical, among others:

  • the filesystem root and its direct children (/usr, /etc…);
  • your home directory, and Windows drive roots;
  • your working directory and its parents;
  • a glob right under a shell variable, like rm -rf "$DIR"/*, because if $DIR is empty, that becomes rm -rf /*.

No allow rule and no hook that returns "allow" can approve such a removal. What happens depends on the mode:

ModeCritical-path removal
default, acceptEdits, planAsks you
autoAsks in the terminal with a 2-minute countdown; elsewhere (desktop app, IDE chat panel, headless runs) denies
dontAskDenies
bypassPermissionsAsks in the terminal with a 2-minute countdown; runs without asking if the new variable is set

The countdown is a nice piece of design for unattended sessions: if nobody answers in two minutes, the command is denied and the agent is told to find another way, so the session keeps working. After three unanswered prompts, further critical removals are denied immediately until you send a new message.

The docs are honest about the limit: this is a check on the text of rm and rmdir commands. A command the check does not recognize gets no special handling, and "other approved commands can delete critical paths too". A script that calls a delete function, or find … -delete, is not an rm. The check is a seatbelt for the obvious case, not a wall.

5. What the new variable does (and when it does nothing)

# macOS / Linux / WSL — only in a disposable environment
export CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1
claude --permission-mode bypassPermissions

Its scope is deliberately narrow:

  • It only works in bypassPermissions mode itself, not in plan mode.
  • It is read from the launch environment only. Put it in a settings file's env block and it is ignored, so a repository cannot quietly switch it on for you.
  • It has no effect when something else answers permission prompts (a hook, a callback in the SDK), when a deny or ask rule covers Bash, when the session runs in the desktop app or IDE chat panel, or when claude is started from inside another session.
  • Claude Code prints a startup line saying whether it took effect, and the docs say: if you see that line and did not set the variable, find where it is set and remove it.

Around it sit other guards that existed before: on Linux and macOS, bypassPermissions refuses to start as root or under sudo (unless inside a recognized sandbox); cloud sessions ignore bypassPermissions and dontAsk from checked-in settings files; and administrators can disable the mode entirely with permissions.disableBypassPermissionsMode: "disable" in managed settings.

7. Choosing a mode for a real situation

SituationReasonable choice
Unfamiliar codebase, or anything touching production credentialsdefault, or plan first and then approve
Day-to-day feature work on your laptopauto (the default), optionally with the Bash sandbox on for defense in depth

8. The general lesson for any agent tool

Every serious coding agent (Claude Code, Codex, Copilot's agent, Cursor and others) ends up with the same three-part design: a mode for the default answer, rules for exceptions, and isolation for the blast radius. The Oct 19 lesson called it "a badge, a locked room and no spare keys". Today's change makes the split very visible:

  • Prompts are a user-experience layer. They help when a human is watching. They cannot stop a command the checker does not understand, and they offer no protection against prompt injection (the docs say this explicitly about bypassPermissions).
  • The boundary is the environment. A container you can throw away makes "the agent deleted everything" a minor event. A laptop with your SSH keys and documents does not.
  • Deny rules are the one control you can rely on across modes. If something must never happen (force-push to main, reading .env), write it as a deny rule rather than hoping a prompt will catch it.
Checklist: know which mode your sessions start in · use dontAsk, not bypass, for CI · put "never" actions in deny rules · run bypass only in disposable containers as non-root · check the startup line for the long variable, and remove it if you did not set it on purpose.

Seis modos de permissão e uma variável de nome enorme: como um agente de código decide quando perguntar

Em 27 de outubro, o Claude Code passou a aceitar uma variável de ambiente chamada CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS. A piada pronta é óbvia, mas a mudança é uma boa desculpa pra entender o sistema de permissões inteiro de um agente de código: o que cada modo libera, quais checagens sobrevivem a todos os modos e por que a linha de segurança de verdade fica em outro lugar.

1. A notícia: o último aviso agora pode ser desligado

O Claude Code tem há tempos uma flag, --dangerously-skip-permissions, que abre a sessão no modo bypassPermissions, em que o agente executa ferramentas sem pedir licença. Segundo o The Register, esse modo apareceu na v1.0.18, em junho de 2025. O que pouca gente sabia: nem esse modo aprovava tudo. Uma lista curta de ações ainda parava pra esperar um humano, e a mais conhecida era apagar um "caminho crítico", como a sua pasta pessoal.

Com a v2.1.311 (lançada por volta de 26–27/10/2026), uma engenheira da Anthropic, Daisy Hollman, avisou que essa última trava agora também pode ser desligada, iniciando o Claude Code com CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1. Muita gente achou que era piada; ela respondeu "Not a joke!". O The Register observou que a mudança não estava no changelog da v2.1.311 quando a matéria saiu. A documentação oficial de modos de permissão agora descreve tudo em detalhe, com um aviso de que, com a variável ligada, um rm -rf ~ pode rodar sem perguntar.

Por que isso é notícia: nada ficou mais perigoso por padrão. A mudança só afeta quem já escolheu o modo mais permissivo e ainda definiu, de propósito, uma segunda variável de nome esquisito no terminal. O interessante é o que ela revela sobre como o sistema de permissões foi montado.

2. Os seis modos, lado a lado

Um modo de permissão define quais ações o agente pode fazer sem te perguntar antes. O Claude Code tem seis. A tabela segue a documentação oficial; "Manual" é o nome que aparece na interface para o valor de configuração default.

ModoRoda sem perguntarPra quê
default (Manual)Só leiturasRevisar cada ação, trabalho sensível
acceptEditsLeituras, edição de arquivos, comandos comuns de sistema de arquivos (mkdir, touch, mv, cp…)Iterar em código que você está revisando
planLeituras (mais comandos aprovados pelo classificador, quando o modo auto está disponível); edições esperam um plano aprovadoExplorar antes de mudar qualquer coisa
autoTudo, com um segundo modelo (o classificador) revisando as ações em segundo planoTarefas longas, menos cansaço de aprovar
dontAskLeituras nas pastas de trabalho e ferramentas pré-aprovadas; o que pediria confirmação é negadoCI e scripts travados
bypassPermissionsTudoSó containers e VMs isolados

Dois detalhes. Primeiro, o auto agora é o modo inicial padrão em sessões interativas no terminal e no VS Code a partir da v2.1.283 (virou padrão em agosto, como vimos aqui em 12/08). Segundo, o dontAsk faz o contrário do que o nome sugere pra muita gente: não é "não pergunta e faz", é "não pergunta e recusa". Por isso ele é a escolha certa pra um job de CI, onde não tem ninguém pra responder.

3. O modo é só a base: quatro camadas

O erro mais comum é achar que o modo conta a história toda. Na prática existem camadas, e algumas valem seja qual for o modo:

1Regras. Você pode escrever regras de allow, ask e deny por ferramenta, como Bash(git push *). Regras de deny bloqueiam em todos os modos, inclusive no bypassPermissions. Já as regras de allow não têm efeito no bypassPermissions (lá tudo já está liberado).
2O modo. Define a resposta padrão pro que nenhuma regra cobre.
3O que nenhum modo aprova sozinho. Regras de ask explícitas, ferramentas que por natureza precisam de um humano (como uma ferramenta de "fazer uma pergunta ao usuário"), ferramentas de conector que a sua organização marcou como "ask" e rm/rmdir reconhecidos em caminhos críticos. É essa lista que a variável nova encurta.
4Isolamento. Sandbox, container ou VM limitam o que uma ação consegue alcançar depois que roda. A documentação resume: o modo decide se o Claude pergunta; o sandbox e o isolamento decidem o que a ação consegue tocar.

No modo auto a ordem é fixa: primeiro as regras; depois leituras e edições dentro da pasta de trabalho são aprovadas direto; todo o resto vai pro classificador; se ele bloquear, o agente recebe o motivo (muitas vezes o nome de uma regra, como [Data Exfiltration]) e precisa tentar outro caminho.

4. Caminhos críticos: a checagem por trás do rm -rf ~

Antes de qualquer rm ou rmdir rodar, o Claude Code olha o alvo. Ele considera críticos, entre outros:

  • a raiz do sistema e as pastas logo abaixo dela (/usr, /etc…);
  • sua pasta pessoal e as raízes de drive no Windows;
  • a pasta de trabalho e as pastas acima dela;
  • um glob logo depois de uma variável de shell, como rm -rf "$DIR"/*, porque se $DIR estiver vazia isso vira rm -rf /*.

Nenhuma regra de allow e nenhum hook que responda "allow" aprova uma remoção dessas. O que acontece depende do modo:

ModoRemoção de caminho crítico
default, acceptEdits, planPergunta
autoPergunta no terminal com contagem de 2 minutos; fora dele (app desktop, chat da IDE, execução headless) nega
dontAskNega
bypassPermissionsPergunta no terminal com contagem de 2 minutos; roda sem perguntar se a variável nova estiver ligada

A contagem regressiva é um bom desenho pra sessões sem ninguém olhando: se ninguém responde em dois minutos, o comando é negado e o agente é avisado pra achar outro caminho, então a sessão continua andando. Depois de três avisos sem resposta, as próximas remoções críticas são negadas na hora, até você mandar uma mensagem nova.

A documentação é honesta sobre o limite: isso é uma checagem no texto dos comandos rm e rmdir. Um comando que ela não reconhece não recebe tratamento especial, e "outros comandos aprovados também podem apagar caminhos críticos". Um script que chama uma função de apagar, ou um find … -delete, não é um rm. A checagem é um cinto de segurança pro caso óbvio, não um muro.

5. O que a variável nova faz (e quando não faz nada)

# macOS / Linux / WSL — só em ambiente descartável
export CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1
claude --permission-mode bypassPermissions

O alcance dela é propositalmente estreito:

  • Só funciona no próprio modo bypassPermissions, não no modo plan.
  • É lida só do ambiente de inicialização. Se você colocar no bloco env de um arquivo de configurações, ela é ignorada, então um repositório não consegue ligá-la escondido pra você.
  • Não tem efeito quando outra coisa responde os pedidos de permissão (um hook, um callback no SDK), quando uma regra de deny ou ask cobre o Bash, quando a sessão roda no app desktop ou no chat da IDE, ou quando o claude é iniciado de dentro de outra sessão.
  • O Claude Code imprime uma linha na inicialização dizendo se ela pegou, e a documentação avisa: se você vê essa linha e não definiu a variável, descubra onde ela está definida e remova.

Em volta dela continuam travas que já existiam: no Linux e no macOS, o bypassPermissions se recusa a iniciar como root ou com sudo (a não ser dentro de um sandbox reconhecido); sessões na nuvem ignoram bypassPermissions e dontAsk vindos de arquivos de configuração do repositório; e administradores podem desligar o modo de vez com permissions.disableBypassPermissionsMode: "disable" nas configurações gerenciadas.

8. A lição geral pra qualquer ferramenta de agente

Todo agente de código sério (Claude Code, Codex, o agente do Copilot, Cursor e outros) acaba no mesmo desenho em três partes: um modo pra resposta padrão, regras pras exceções e isolamento pro raio de estrago. A lição de 19/10 chamou isso de "um crachá, uma sala trancada e nenhuma chave reserva". A mudança de hoje deixa essa divisão bem visível:

  • Avisos de permissão são uma camada de experiência do usuário. Ajudam quando tem um humano olhando. Não param um comando que o verificador não entende, e não protegem contra prompt injection (a documentação diz isso com todas as letras sobre o bypassPermissions).
  • A fronteira é o ambiente. Num container que você pode jogar fora, "o agente apagou tudo" é um incidente pequeno. Num notebook com suas chaves SSH e documentos, não.
  • Regras de deny são o único controle que vale em todos os modos. Se algo nunca pode acontecer (force-push na main, ler o .env), escreva como regra de deny em vez de torcer pra um aviso pegar.
Checklist: saiba em qual modo suas sessões começam · use dontAsk, não bypass, no CI · coloque as ações "nunca" em regras de deny · rode bypass só em containers descartáveis e sem root · confira a linha de inicialização da variável longa e remova se não foi você que ligou de propósito.
