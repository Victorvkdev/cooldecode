Mixture of Experts: a huge model that only wakes up a small part of itself

When a model is announced as "1 trillion parameters, 49 billion active", the second number is the one that sets the speed. Mixture of Experts (MoE) is the architecture behind that split, and it comes with a catch the headline never mentions: memory.

1. Dense models: everyone works on every token

A transformer block has two main parts: attention (covered in the attention and KV cache lesson) and a feed-forward network (FFN), a small neural network applied to each token separately. The FFN holds a large share of the model's parameters. In a dense model, every token goes through the same FFN, in every layer. Double the parameters and you roughly double the work per token.

2. MoE: a router and a pool of experts

A mixture-of-experts model replaces that single FFN with several FFNs called experts, plus a small learned network called the router. For each token, the router scores every expert, keeps the best k (this is "top-k"), sends the token only through those, and combines their outputs weighted by the router's scores. In Sebastian Raschka's simplified form: MoE(x) = Σ g_i(x) · E_i(x) over the chosen experts.

Analogy: a hospital. A dense model is a single doctor who handles every patient. An MoE model is a hospital with eight specialists and a triage nurse (the router). Each patient sees only two of them. The hospital knows a lot (eight doctors' worth), but each visit costs the time of two.

Three details worth knowing, all from the sources below:

  • Routing is per token and per layer. Two tokens of the same sentence can use different experts, and each layer makes its own choice.
  • Only the FFN is replaced. Attention usually stays dense and runs for every token.
  • Some designs add a shared expert that is always active next to the routed ones, to handle common patterns and let the others specialize.

A tiny router in plain JavaScript:

function route(scores, k) {
  // scores: one number per expert (the router's output)
  const top = scores
    .map((s, i) => ({ i, s }))
    .sort((a, b) => b.s - a.s)
    .slice(0, k);                          // keep the k best experts
  const sum = top.reduce((t, e) => t + Math.exp(e.s), 0);
  return top.map(e => ({ expert: e.i, weight: Math.exp(e.s) / sum }));
}
route([0.1, 2.0, -1, 0.4, 1.5, 0, -0.5, 0.2], 2);
// [{expert: 1, weight: 0.62}, {expert: 4, weight: 0.38}]

3. Try it: route a sentence

This is a toy: the router scores here come from a fixed hash of each word, not from a trained model, so the experts do not "mean" anything. What it shows is the shape of the mechanism. Pick a word to see its experts, change k, and switch between a balanced router and a collapsed one.

In the collapsed mode, the router sends almost every token to the same one or two experts. Those become a bottleneck while the rest sit idle, which is what the training techniques in section 5 exist to prevent.

4. Total vs active parameters

This creates two numbers. Total parameters count every expert stored in the checkpoint. Active parameters count the shared parts plus the experts actually selected for one token. Names like 235B-A22B encode both: roughly 235 billion total, 22 billion active.

Figures for the first three come from the ZeroEntropy concept page; the fourth is from the earlier lesson on Mistral Large 4 and is the vendor's own number. This is why MoE took over the open-weight frontier: scaling laws say more parameters means better quality, and MoE lets you add parameters without paying the full compute bill on every token.

Careful with "active": active parameters are only an approximation of runtime cost. Attention, embeddings and the output layer still run, and routing adds its own overhead (scoring, sorting, moving tokens between chips). A 22B-active MoE will not necessarily have the latency of a dense 22B model (Raschka).

5. The training problem: expert collapse

The router and the experts learn together. Left alone, gradient descent finds a lazy shortcut: send everything to one expert, train it hard, ignore the others. That is expert collapse, and the unused experts become dead weight.

The standard fixes, per ZeroEntropy and Raschka:

  • Auxiliary load-balancing loss: an extra penalty in training that grows when some experts get much more traffic than others (the Switch Transformer approach).
  • Routing bias: DeepSeek's "auxiliary-loss-free" variant nudges the router scores toward under-used experts at each step.
  • Expert capacity limits: cap how many tokens one expert may take per batch.

Experts also do not become tidy "math expert" or "grammar expert" modules. Both sources say specialization is messier: it shows up more at the level of token types, syntax or position than at human-friendly topics. Think "emergent partitions", not "departments".

6. The catch: memory and serving

Sparse activation saves arithmetic, not storage. Every expert must live somewhere, and the router can pick any of them for the next token. Try the sizing tool:

–

With 16-bit weights, Mixtral's 47B parameters need about 94 GB just to hold the weights, the same as a dense 47B model, even though each token only computes with about 13B of them (ZeroEntropy). The compute discount is real; the memory discount is zero. Practical consequences:

  • Size deployments by total parameters, then treat the speed as a bonus. ZeroEntropy warns that teams sizing by active count under-provision by 3-4x.
  • Routing breaks the easy case for GPUs. Different tokens go to different experts, so batches fragment, and when experts are spread across chips, tokens must travel to the chip that owns their expert and back. This all-to-all communication can become a big share of serving time. Serving stacks like vLLM and SGLang have specialized MoE kernels, but throughput per active parameter is still worse than dense.
  • The KV cache is not shrunk by MoE. MoE changes the FFN path; the cache lives in attention, so the memory lesson from the KV cache still applies on top.

7. What this means for you as a developer

Read model names with two numbers in mind

When a launch post says "1T parameters", ask: total or active? Cost and speed follow the active count; the hardware you need to self-host follows the total.

Self-hosting an open MoE model

Before downloading, compute total parameters × bytes per weight and compare with your GPU memory. Quantizing to 8 or 4 bits shrinks it (use the tool above), but it is a trade of some quality for fit.

Using an API

You never see the experts. For API users, MoE shows up only indirectly, as the reason a very large model can be priced and served at a speed that a dense model of the same total size could not manage. Whether a given closed model is dense or MoE is usually not published: ZeroEntropy says GPT-4 is "widely reported" as MoE and Claude "reportedly" dense, so treat both as unconfirmed.

A short exercise

A model is listed as 400B-A20B. (1) What share of parameters is active per token? (2) How much memory do the weights alone need at FP8? Answers: (1) 20/400 = 5%. (2) 400B × 1 byte = about 400 GB, before any KV cache. Now check it in the tool above by typing 400 and 20.

Mixture of Experts: um modelo enorme que só acorda uma pequena parte de si

Quando um modelo é anunciado como "1 trilhão de parâmetros, 49 bilhões ativos", o segundo número é o que define a velocidade. Mixture of Experts (MoE) é a arquitetura por trás dessa divisão, e vem com uma pegadinha que a manchete nunca cita: memória.

1. Modelos densos: todo mundo trabalha em todo token

Um bloco de transformer tem duas partes principais: a atenção (da lição sobre atenção e KV cache) e uma rede feed-forward (FFN), uma redezinha neural aplicada a cada token separadamente. A FFN concentra boa parte dos parâmetros do modelo. Num modelo denso, todo token passa pela mesma FFN, em todas as camadas. Dobrar os parâmetros significa, grosso modo, dobrar o trabalho por token.

2. MoE: um roteador e um grupo de especialistas

Um modelo mixture-of-experts troca essa FFN única por várias FFNs chamadas especialistas (experts), mais uma pequena rede aprendida chamada roteador (router). Para cada token, o roteador dá uma nota a cada especialista, fica com os k melhores ("top-k"), manda o token só por eles e combina as saídas ponderadas pelas notas. Na forma simplificada de Sebastian Raschka: MoE(x) = Σ g_i(x) · E_i(x) sobre os especialistas escolhidos.

Analogia: um hospital. Um modelo denso é um único médico que atende todos os pacientes. Um modelo MoE é um hospital com oito especialistas e uma enfermeira de triagem (o roteador). Cada paciente passa só por dois deles. O hospital sabe muito (o conhecimento de oito médicos), mas cada consulta custa o tempo de dois.

Três detalhes importantes, todos das fontes abaixo:

  • O roteamento é por token e por camada. Dois tokens da mesma frase podem usar especialistas diferentes, e cada camada faz a própria escolha.
  • Só a FFN é substituída. A atenção normalmente continua densa e roda para todo token.
  • Alguns projetos adicionam um especialista compartilhado, sempre ativo ao lado dos roteados, para cuidar dos padrões comuns e deixar os outros se especializarem.

Um roteador minúsculo em JavaScript puro:

function route(scores, k) {
  // scores: um número por especialista (a saída do roteador)
  const top = scores
    .map((s, i) => ({ i, s }))
    .sort((a, b) => b.s - a.s)
    .slice(0, k);                          // fica com os k melhores
  const sum = top.reduce((t, e) => t + Math.exp(e.s), 0);
  return top.map(e => ({ expert: e.i, weight: Math.exp(e.s) / sum }));
}
route([0.1, 2.0, -1, 0.4, 1.5, 0, -0.5, 0.2], 2);
// [{expert: 1, weight: 0.62}, {expert: 4, weight: 0.38}]

3. Teste: roteie uma frase

Isto é um brinquedo: as notas do roteador aqui vêm de um hash fixo de cada palavra, não de um modelo treinado, então os especialistas não "significam" nada. O que ele mostra é o formato do mecanismo. Escolha uma palavra para ver seus especialistas, mude o k e alterne entre um roteador balanceado e um colapsado.

No modo colapsado, o roteador manda quase todos os tokens para o mesmo um ou dois especialistas. Eles viram gargalo enquanto o resto fica parado, e é isso que as técnicas de treino da seção 5 existem para evitar.

4. Parâmetros totais vs ativos

Isso cria dois números. Parâmetros totais contam todos os especialistas guardados no checkpoint. Parâmetros ativos contam as partes compartilhadas mais os especialistas realmente escolhidos para um token. Nomes como 235B-A22B codificam os dois: cerca de 235 bilhões no total, 22 bilhões ativos.

ModeloTotalAtivos por tokenFatia ativa

Grok-1314B~86B~27%
DeepSeek-V3671B37B~5,5%
Mistral Large 4 (nossa lição de 13/10)~1T~49B~5%

Os números dos três primeiros vêm da página de conceitos da ZeroEntropy; o quarto vem da lição anterior sobre o Mistral Large 4 e é o número do próprio fabricante. Por isso o MoE dominou a fronteira dos modelos de pesos abertos: as leis de escala dizem que mais parâmetros significa mais qualidade, e o MoE permite somar parâmetros sem pagar a conta inteira de cálculo a cada token.

Cuidado com "ativo": parâmetros ativos são só uma aproximação do custo em execução. Atenção, embeddings e a camada de saída continuam rodando, e o roteamento acrescenta custo próprio (pontuar, ordenar, mover tokens entre chips). Um MoE de 22B ativos não necessariamente tem a latência de um modelo denso de 22B (Raschka).

5. O problema do treino: colapso de especialistas

O roteador e os especialistas aprendem juntos. Se ninguém intervir, a descida do gradiente acha um atalho preguiçoso: mandar tudo para um especialista, treiná-lo forte e ignorar os outros. Isso é o colapso de especialistas, e os especialistas sem uso viram peso morto.

As correções padrão, segundo ZeroEntropy e Raschka:

  • Perda auxiliar de balanceamento: uma penalidade extra no treino que cresce quando alguns especialistas recebem muito mais tráfego que outros (a abordagem do Switch Transformer).
  • Viés de roteamento: a variante "sem perda auxiliar" da DeepSeek empurra as notas do roteador para os especialistas subutilizados a cada passo.
  • Limites de capacidade: limitar quantos tokens um especialista aceita por lote.

Os especialistas também não viram módulos arrumadinhos de "especialista em matemática" ou "em gramática". As duas fontes dizem que a especialização é mais bagunçada: aparece mais no nível de tipos de token, sintaxe ou posição do que em assuntos que um humano reconheceria. Pense em "partições emergentes", não em "departamentos".

6. A pegadinha: memória e serviço

Ativação esparsa economiza aritmética, não armazenamento. Todo especialista precisa estar em algum lugar, e o roteador pode escolher qualquer um para o próximo token. Teste a ferramenta de dimensionamento:

–

Com pesos de 16 bits, os 47B parâmetros do Mixtral precisam de cerca de 94 GB só para guardar os pesos, o mesmo de um modelo denso de 47B, embora cada token calcule com uns 13B deles (ZeroEntropy). O desconto de cálculo é real; o desconto de memória é zero. Consequências práticas:

  • Dimensione a infraestrutura pelos parâmetros totais e trate a velocidade como bônus. A ZeroEntropy avisa que times que dimensionam pelo número de ativos subestimam em 3-4x.
  • O roteamento complica o caso fácil das GPUs. Tokens diferentes vão para especialistas diferentes, então os lotes se fragmentam, e quando os especialistas ficam espalhados em vários chips, os tokens precisam viajar até o chip do especialista e voltar. Essa comunicação all-to-all pode virar uma fatia grande do tempo de serviço. Stacks como vLLM e SGLang têm kernels especializados para MoE, mas a vazão por parâmetro ativo ainda é pior que a de um modelo denso.
  • O KV cache não encolhe com MoE. O MoE muda o caminho da FFN; o cache vive na atenção, então a lição de memória do KV cache continua valendo por cima.

7. O que isso significa para você, dev

Leia nomes de modelo com dois números na cabeça

Quando um post de lançamento diz "1T de parâmetros", pergunte: total ou ativo? Custo e velocidade seguem o número de ativos; o hardware necessário para hospedar por conta própria segue o total.

Hospedando um modelo MoE aberto

Antes de baixar, calcule parâmetros totais × bytes por peso e compare com a memória da sua GPU. Quantizar para 8 ou 4 bits reduz (use a ferramenta acima), mas é trocar um pouco de qualidade por encaixe.

Usando uma API

Você nunca vê os especialistas. Para quem usa API, o MoE aparece só indiretamente, como o motivo de um modelo muito grande poder ser vendido e servido numa velocidade que um modelo denso do mesmo tamanho total não alcançaria. Se um modelo fechado é denso ou MoE geralmente não é publicado: a ZeroEntropy diz que o GPT-4 é "amplamente reportado" como MoE e o Claude "reportadamente" denso, então trate ambos como não confirmados.

Um exercício rápido

Um modelo aparece como 400B-A20B. (1) Que fatia dos parâmetros fica ativa por token? (2) Quanta memória só os pesos exigem em FP8? Respostas: (1) 20/400 = 5%. (2) 400B × 1 byte = cerca de 400 GB, antes de qualquer KV cache. Confira na ferramenta acima digitando 400 e 20.
