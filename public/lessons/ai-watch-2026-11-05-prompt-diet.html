The prompt diet: how to cut 80% of an old prompt without losing quality

Anthropic says it deleted over 80% of Claude Code's system prompt for its newest models with no measurable loss on its coding evals. Most of us are still carrying prompts written for older models: ALL CAPS rules, "double-check everything", walls of examples, the same instruction three times. A practical audit: what to cut, what to rewrite, what to keep, and a small linter to try it on your own prompt.

1. Why old prompts age badly

A prompt is written against a specific model's weaknesses. In 2024 a model might ignore an instruction unless you shouted it, forget a rule placed at the start of a long context, or invent a tool call unless you showed three examples. So we shouted, repeated and over-specified. Those patches stayed in the file after the weakness went away.

In a July 24, 2026 post, Anthropic's Thariq Shihipar described what happened when the Claude Code team audited its own prompt: "We removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5 with no measurable loss on our coding evaluations." The diagnosis was that Claude was being overconstrained. Reading internal transcripts, they found single requests carrying contradictory messages like "leave documentation as appropriate" and "DO NOT add comments", coming from the system prompt, a skill and the user at the same time. The model can usually untangle that, but it has to spend effort deciding which voice to obey.

The core idea: every old rule has a cost now. It either does nothing (wasted tokens), or it fights the model's own judgement on the cases where the rule is wrong, or it contradicts another rule somewhere else in the context.

2. Six "then vs now" shifts

These come from Anthropic's July post and its prompt engineering guide. One item (self-verification) comes from a third-party summary, flagged below.

ThenNowWhy
Give hard rules ("never write multi-line comments")State the principle and let the model judge ("match the surrounding code's comment density")Hard rules are wrong for some subset of cases; newer models handle the judgement
Show examples of how to use each toolDesign expressive interfaces (clear parameter names, enums, short descriptions)Anthropic found tool-usage examples narrow the model's exploration
Put everything up frontProgressive disclosure: load detailed guidance only when needed (skills, linked files)Rarely-used instructions dilute the ones that matter right now
Repeat key instructions (top, bottom, tool description)Say it once, in the place where it appliesOlder models over-weighted the end of the context; newer ones don't need the echo
"NEVER do X" / "Don't use bullet points"Say what to do, with the reason ("write flowing paragraphs, because this is read aloud")A positive target plus a reason generalizes to cases you didn't list
"Before you finish, double-check every number"Define what "done" looks like and how it can be verifiedPer MindStudio's reading of Anthropic's Opus guidance, generic self-check instructions now add a slow, redundant pass

A closer look at three of them

Rules → judgement. Anthropic shared its own before and after. Old system prompt: "In code: default to writing no comments. Never write multi-paragraph docstrings or multi-line comment blocks — one short line max." New one: "Write code that reads like the surrounding code: match its comment density, naming, and idiom." The new line is shorter and right in more situations, for example in a codebase where long docstrings are the convention.

Examples → interfaces. This looks like it contradicts our October 9 lesson ("Show, don't tell"). It doesn't, if you separate two jobs. Examples are still the best way to pin down an output format (a summary style, a JSON shape). What the Claude Code team dropped were examples of how to use tools, because they anchor the model to the cases you happened to show. Their alternative: make the tool explain itself. A status parameter typed as "pending" | "in_progress" | "completed" already teaches the workflow; one sentence ("keep exactly one item in_progress") covers the rest.

Prohibition → target + reason. Anthropic's guide: "NEVER use bullet points" is less effective than explaining that you prefer flowing prose and why. A reason gives the model a principle to apply to cases you never wrote down. If the reason is "this will be read by a text-to-speech engine", the model can also avoid tables, emoji and ellipses without you listing each one.

3. A full before/after refactor

A generic system prompt for an internal "release notes writer" bot, written the 2024 way:

You are a WORLD-CLASS technical writer with 20 years of experience.
IMPORTANT: You MUST follow ALL rules below. This is CRITICAL.

RULES:
1. NEVER use emojis.
2. NEVER use the word "simply".
3. DO NOT write more than 200 words.
4. ALWAYS use bullet points.
5. Before answering, double-check every item against the commit list.
6. Do not invent features.

Example 1: [40 lines of a past release note]
Example 2: [40 lines of another one]
Example 3: [40 lines of another one]

REMEMBER: NEVER use emojis and NEVER exceed 200 words!!!

The same intent, rewritten:

You turn a list of merged commits into release notes for customers of a
B2B web app. Readers are account admins, not developers: they want to know
what changed for them and whether they need to do anything.

Write a short bulleted list (about 200 words at most, since it is shown
inside an in-app banner), grouped as New, Improved and Fixed. Use a plain,
calm tone; no emojis, since the banner renders them inconsistently.

Only describe changes that appear in the commits. If a commit is unclear,
leave it out and list its hash under "Needs review" at the end.

Done means: every bullet maps to at least one commit, nothing internal-only
(refactors, CI) is mentioned, and an admin could act on it without asking.

Format reference: <one short example of a past note>

What changed and why:

  • Persona removed. "World-class, 20 years" adds nothing measurable; the audience and purpose do the work. (MindStudio cites a 162-persona test with no gain for Claude; we didn't read that study directly.)
  • Urgency removed. "IMPORTANT / CRITICAL / MUST" in caps. Newer models tend to over-react to urgency language, and if everything is critical, nothing is.
  • Every constraint now has a reason. The 200-word limit is tied to the banner, the emoji ban to rendering. If the banner gets bigger, the model (and the next human editing the prompt) knows the rule is related to it.
  • "Double-check" became a definition of done. Instead of asking for a vague second pass, the prompt states what a correct result looks like, which is also something you can test.
  • "Don't invent" became an escape hatch. Giving the model a legitimate place to put uncertain items ("Needs review") works better than forbidding guesses.
  • Three examples became one. Enough to pin the format; fewer details to over-copy.
  • The closing echo is gone. Said once, in context.

Roughly: from ~140 lines (with examples) to ~20, and every remaining line explains itself.

    5. What you should NOT cut

    The diet is about removing patches, not information. Keep:

    • Things the model cannot know. Your audience, your business rules, where the output goes, the quirks of your codebase. Anthropic's advice for CLAUDE.md files is exactly this: keep it light, but "spend most of the tokens on gotchas", and skip what the model can see for itself in the files.
    • Hard constraints that really are hard. Security boundaries, legal wording, data that must never leave a system. The blog itself says to avoid over-constraining "except in highly important areas".
    • Format examples where the format is the product. A parser downstream that breaks on a different shape is a real constraint; one good example is cheap insurance.
    • Anything your evals show still helps. If removing a line makes results worse on your test set, it stays, whatever any guide says.

    6. A safe process for slimming a prompt

    1. Collect 10-30 real inputs and save the current outputs. That is your baseline.
    2. Remove in groups, not all at once: first urgency/caps, then duplicated instructions, then personas, then tool examples.
    3. Rewrite every surviving "never" as a target plus a reason.
    4. Move rare, long guidance out into a file or skill the model loads on demand.
    5. Re-run the same inputs after each step and compare. Keep a change only if outputs are as good or better.
    6. Apply the colleague test (Anthropic's "golden rule", as summarized by MindStudio): would a smart new teammate with zero context understand what to do and why?

    If you use Claude Code, the July post says Anthropic packaged these practices into a /doctor check that helps right-size skills and CLAUDE.md files. We have not tested it for this lesson.

    7. Caveats

    • Model-specific. The 80% figure is about Claude Code on Opus 5 / Fable 5-class models and Anthropic's own coding evals. A smaller or older model, or another vendor's, may still need the scaffolding.
    • "No measurable loss" ≠ "no change". It means no drop on their benchmarks, not identical behaviour in every case.
    • The self-verification point is secondhand. It comes from MindStudio's reading of Anthropic's Opus guidance; we could not open Anthropic's prompting docs page directly today. A specific, checkable verification step (run the tests, compare totals with the source) is still a good idea; what loses value is the generic "double-check your work".
    • Shorter is not the goal. Clearer is. Anthropic's guide puts it well: the best prompt "achieves your goals reliably with the minimum necessary structure".

    1. Por que prompts antigos envelhecem mal

    Um prompt é escrito contra as fraquezas de um modelo específico. Em 2024, um modelo podia ignorar uma instrução se você não gritasse, esquecer uma regra colocada no começo de um contexto longo, ou inventar uma chamada de ferramenta se você não mostrasse três exemplos. Então a gente gritava, repetia e especificava demais. Esses remendos ficaram no arquivo depois que a fraqueza sumiu.

    Num post de 24 de julho de 2026, Thariq Shihipar, da Anthropic, contou o que aconteceu quando o time do Claude Code auditou o próprio prompt: "Removemos mais de 80% do system prompt do Claude Code para modelos como Claude Opus 5 e Claude Fable 5, sem perda mensurável nas nossas avaliações de código." O diagnóstico foi que o Claude estava restrito demais. Lendo transcrições internas, eles acharam pedidos únicos carregando mensagens contraditórias como "deixe documentação quando apropriado" e "NÃO adicione comentários", vindas do system prompt, de uma skill e do usuário ao mesmo tempo. O modelo geralmente consegue desatar esse nó, mas gasta esforço decidindo qual voz obedecer.

    A ideia central: toda regra antiga tem um custo agora. Ou ela não faz nada (tokens desperdiçados), ou ela briga com o julgamento do próprio modelo nos casos em que a regra está errada, ou ela contradiz outra regra em algum outro ponto do contexto.

    2. Seis mudanças "antes vs agora"

    Elas vêm do post de julho da Anthropic e do guia de prompt engineering dela. Um item (autoverificação) vem de um resumo de terceiros, sinalizado abaixo.

    AntesAgoraPor quê
    Dar regras rígidas ("nunca escreva comentários de várias linhas")Dizer o princípio e deixar o modelo julgar ("siga a densidade de comentários do código ao redor")Regras rígidas erram em parte dos casos; modelos novos dão conta do julgamento
    Mostrar exemplos de como usar cada ferramentaDesenhar interfaces expressivas (nomes de parâmetro claros, enums, descrições curtas)A Anthropic viu que exemplos de uso de ferramenta estreitam a exploração do modelo
    Colocar tudo de uma vez no começoRevelação progressiva: carregar orientação detalhada só quando precisa (skills, arquivos linkados)Instruções raramente usadas diluem as que importam agora
    Repetir instruções-chave (topo, final, descrição da ferramenta)Dizer uma vez, no lugar onde se aplicaModelos antigos davam peso demais ao fim do contexto; os novos não precisam do eco
    "NUNCA faça X" / "Não use bullet points"Dizer o que fazer, com o motivo ("escreva parágrafos corridos, porque isso vai ser lido em voz alta")Um alvo positivo com motivo se generaliza para casos que você não listou
    "Antes de terminar, confira cada número duas vezes"Definir o que é "pronto" e como dá pra verificarSegundo a leitura da MindStudio sobre o guia do Opus, instruções genéricas de autoconferência hoje só adicionam uma passada lenta e redundante

    Olhando mais de perto três delas

    Regras → julgamento. A Anthropic mostrou o próprio antes e depois. System prompt antigo: "Em código: por padrão, não escreva comentários. Nunca escreva docstrings de vários parágrafos ou blocos de comentário de várias linhas — no máximo uma linha curta." O novo: "Escreva código que leia como o código ao redor: siga a densidade de comentários, os nomes e o estilo dele." A linha nova é mais curta e acerta em mais situações, por exemplo num codebase onde docstrings longas são a convenção.

    Exemplos → interfaces. Isso parece contradizer a nossa lição de 9 de outubro ("Mostre, não diga"). Não contradiz, se você separar dois trabalhos. Exemplos continuam sendo o melhor jeito de fixar um formato de saída (um estilo de resumo, um formato de JSON). O que o time do Claude Code tirou foram exemplos de como usar ferramentas, porque eles prendem o modelo aos casos que você calhou de mostrar. A alternativa deles: fazer a ferramenta se explicar sozinha. Um parâmetro status tipado como "pending" | "in_progress" | "completed" já ensina o fluxo; uma frase ("mantenha exatamente um item in_progress") cobre o resto.

    Proibição → alvo + motivo. Pelo guia da Anthropic, "NUNCA use bullet points" funciona pior do que explicar que você prefere texto corrido e por quê. Um motivo dá ao modelo um princípio para aplicar em casos que você nunca escreveu. Se o motivo é "isso vai ser lido por um sintetizador de voz", o modelo também consegue evitar tabelas, emojis e reticências sem você listar cada um.

    3. Uma refatoração completa, antes e depois

    Um system prompt genérico de um bot interno "redator de release notes", escrito do jeito de 2024:

    Você é um redator técnico de NÍVEL MUNDIAL com 20 anos de experiência.
IMPORTANTE: Você DEVE seguir TODAS as regras abaixo. Isso é CRÍTICO.

REGRAS:
1. NUNCA use emojis.
2. NUNCA use a palavra "simplesmente".
3. NÃO escreva mais de 200 palavras.
4. SEMPRE use bullet points.
5. Antes de responder, confira cada item com a lista de commits.
6. Não invente funcionalidades.

Exemplo 1: [40 linhas de uma release note antiga]
Exemplo 2: [40 linhas de outra]
Exemplo 3: [40 linhas de outra]

LEMBRE-SE: NUNCA use emojis e NUNCA passe de 200 palavras!!!

    A mesma intenção, reescrita:

    Você transforma uma lista de commits mergeados em release notes para
clientes de um web app B2B. Quem lê são admins de conta, não devs: querem
saber o que mudou pra eles e se precisam fazer alguma coisa.

Escreva uma lista curta em bullets (umas 200 palavras no máximo, porque
aparece dentro de um banner no app), agrupada em Novo, Melhorado e
Corrigido. Tom simples e calmo; sem emojis, porque o banner renderiza
emojis de forma inconsistente.

Só descreva mudanças que aparecem nos commits. Se um commit não estiver
claro, deixe de fora e liste o hash dele em "Precisa de revisão" no fim.

Pronto significa: cada bullet corresponde a pelo menos um commit, nada
puramente interno (refactors, CI) aparece, e um admin consegue agir sem
precisar perguntar.

Referência de formato: <um exemplo curto de uma nota antiga>

    O que mudou e por quê:

    • Persona removida. "Nível mundial, 20 anos" não acrescenta nada mensurável; o público e o propósito fazem o trabalho. (A MindStudio cita um teste com 162 personas sem ganho para o Claude; não lemos esse estudo diretamente.)
    • Urgência removida. "IMPORTANTE / CRÍTICO / DEVE" em caixa alta. Modelos novos tendem a reagir demais a linguagem de urgência, e se tudo é crítico, nada é.
    • Toda restrição agora tem motivo. O limite de 200 palavras está ligado ao banner, a proibição de emoji à renderização. Se o banner crescer, o modelo (e a próxima pessoa que editar o prompt) sabe de onde a regra vem.
    • "Confira" virou definição de pronto. Em vez de pedir uma segunda passada vaga, o prompt diz como é um resultado correto, o que também é algo que você consegue testar.
    • "Não invente" virou válvula de escape. Dar ao modelo um lugar legítimo para itens incertos ("Precisa de revisão") funciona melhor do que proibir chute.
    • Três exemplos viraram um. Suficiente para fixar o formato, com menos detalhe para ser copiado à toa.
    • O eco do final sumiu. Dito uma vez, no contexto certo.

    Mais ou menos: de ~140 linhas (com os exemplos) para ~20, e cada linha que sobrou se explica sozinha.

    4. Teste: um linter de dieta de prompt

    Cole qualquer prompt (ou use o exemplo). Roda no seu navegador com correspondência de padrões simples. É um checklist, não um juiz: um alerta quer dizer "olhe essa linha", não "isso está errado".

      5. O que você NÃO deve cortar

      A dieta é sobre tirar remendos, não informação. Mantenha:

      • O que o modelo não tem como saber. Seu público, suas regras de negócio, pra onde a saída vai, as manias do seu codebase. O conselho da Anthropic para arquivos CLAUDE.md é exatamente esse: deixe leve, mas "gaste a maior parte dos tokens nas pegadinhas", e pule o que o modelo consegue ver sozinho nos arquivos.
      • Restrições que são duras de verdade. Limites de segurança, texto jurídico, dados que nunca podem sair de um sistema. O próprio post diz para evitar restringir demais "exceto em áreas muito importantes".
      • Exemplos de formato quando o formato é o produto. Um parser lá na frente que quebra com outro formato é uma restrição real; um bom exemplo é um seguro barato.
      • Tudo que seus testes mostram que ainda ajuda. Se tirar uma linha piora os resultados no seu conjunto de testes, ela fica, diga o guia que disser.

      6. Um processo seguro para enxugar um prompt

      1. Junte 10 a 30 entradas reais e salve as saídas atuais. Essa é sua linha de base.
      2. Tire em grupos, não tudo de uma vez: primeiro urgência/caixa alta, depois instruções duplicadas, depois personas, depois exemplos de ferramenta.
      3. Reescreva todo "nunca" que sobreviver como alvo + motivo.
      4. Mova orientação longa e rara para fora, num arquivo ou skill que o modelo carrega sob demanda.
      5. Rode as mesmas entradas de novo depois de cada passo e compare. Só mantenha uma mudança se as saídas ficarem iguais ou melhores.
      6. Aplique o teste do colega (a "regra de ouro" da Anthropic, no resumo da MindStudio): um colega esperto, recém-chegado e sem nenhum contexto entenderia o que fazer e por quê?

      Se você usa o Claude Code, o post de julho diz que a Anthropic empacotou essas práticas numa verificação /doctor que ajuda a dimensionar skills e arquivos CLAUDE.md. Não testamos isso para esta lição.

      7. Ressalvas

      • Depende do modelo. O número de 80% é sobre o Claude Code em modelos da classe Opus 5 / Fable 5 e nos testes de código da própria Anthropic. Um modelo menor ou mais antigo, ou de outra empresa, pode ainda precisar dos andaimes.
      • "Sem perda mensurável" ≠ "nada mudou". Quer dizer que não caiu nos benchmarks deles, não que o comportamento é idêntico em todo caso.
      • O ponto sobre autoverificação é de segunda mão. Vem da leitura da MindStudio sobre o guia do Opus; não conseguimos abrir hoje a página de prompting da documentação da Anthropic. Um passo de verificação específico e checável (rodar os testes, comparar totais com a fonte) continua sendo boa ideia; o que perde valor é o genérico "confira seu trabalho".
      • Curto não é o objetivo. Claro é. O guia da Anthropic resume bem: o melhor prompt é o que "atinge seus objetivos de forma confiável com o mínimo de estrutura necessária".
