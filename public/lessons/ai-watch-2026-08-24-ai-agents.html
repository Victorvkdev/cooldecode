What actually makes something an "AI agent"

"Agent" got slapped onto every product this year, but underneath the marketing there's one real architectural difference between a chatbot and an agent: a loop. Here's what's inside it, and why nearly everything Anthropic shipped in August 2026 — auto mode, computer use, the browser tool — is that same loop wearing different clothes.

1. Chatbot vs. agent: the one real difference

A chatbot takes your message, produces a reply, and stops. Every "turn" is one round trip: you write, it writes back, the conversation waits for you again. Nothing happens in between except the model generating tokens.

An agent is the same underlying model, but wired into a loop that doesn't need you between steps. Give it a goal — "find the three cheapest flights next Friday and book the best one" — and it can search, read results, compare, decide it's missing information, search again, and only come back to you once the goal is actually done (or it needs a decision only you can make, like a credit card number).

That's the whole distinction. Not a bigger model, not more "intelligence" in the abstract sense — a different control structure wrapped around the same kind of model that powers a chatbot.

2. The loop: perceive, decide, act, observe

Every agent, regardless of vendor or framework, runs some version of the same four-step cycle:

  • Perceive — read the current state: the user's goal, a screenshot, a file, a database row, the result of the last action.
  • Decide — the model reasons about what to do next given the goal and what it just perceived. This is the step people call "the agentic loop" or "reasoning-action cycle" — it's genuinely just the model picking the next move.
  • Act — the model calls a tool: run a search, click a button, execute code, write a file, query a database.
  • Observe — the result of that action becomes new input, and the loop goes back to step 1.

A chatbot runs this loop once and prints text. An agent runs it as many times as the goal requires — sometimes twice, sometimes forty times — revising its plan at every pass based on what actually happened, not just what it expected to happen.

Worked example

Goal: "Summarize the top cited paper on agent memory from this year." The agent reasons it needs a search tool, calls it with a query, gets back 15 results with citation counts, picks the one with the most citations, calls a document-retrieval tool to pull the abstract, decides that's enough context, and writes the summary. Four loop passes, three tool calls, zero human intervention after the initial goal.

3. Why tool use is the key ingredient

None of this works without a standard way for the model to call tools. In practice that means: a tool gets defined with a name, a description, and a schema for its parameters — the model doesn't need custom code per tool, it just needs to see the schema and decide when to use it.

This is exactly the gap the Model Context Protocol (MCP) was built to close — standardizing how an agent discovers and calls tools and data sources instead of every app writing bespoke integration code for every model. It's why MCP adoption exploded through 2026 alongside the agent boom: more agents needing tools means more demand for one shared way to plug tools in.

Anthropic's own computer use and browser use tools, which went generally available on the Claude Platform on August 20, 2026, are a direct expression of this idea taken further: instead of the model only calling narrow, purpose-built tools, it can act on software that has no API at all — clicking, typing, and scrolling a screenshot the way a person would, or reading a webpage's actual structure and acting on a specific field or button rather than a pixel coordinate.

4. Single agent vs. multi-agent orchestration

Simple tasks fit inside one agent running one loop. But once a goal has genuinely independent sub-parts — research one thing while drafting another, or verify a claim while a separate step keeps working — a single loop becomes a bottleneck: everything is serialized through one line of reasoning.

The pattern that's become standard by mid-2026 is multi-agent orchestration: a lead agent breaks the goal into sub-tasks and hands each one to a specialized sub-agent (a "researcher," a "coder," a "verifier"), then merges their outputs. This isn't just parallelism for speed — it also isolates context, so one sub-agent's noisy exploration doesn't pollute the reasoning of another.

Trade-off to keep in mind: multi-agent setups cost more (every sub-agent burns its own tokens) and add coordination overhead (someone has to reconcile disagreeing sub-agent outputs). They're worth it when sub-tasks are genuinely independent — not as a default for everything.

5. Where this shows up right now, concretely

You don't need an exotic example — three things Anthropic shipped or changed in the last few weeks are this same loop in production, at different scopes:

ProductWhat the loop acts on
Claude Code auto mode (default since Aug 14, 2026)Files and shell commands in a codebase — the loop reads code, decides what to change, edits/runs commands, observes the result (tests pass or fail), repeats.
Computer use tool (GA Aug 20, 2026)Any desktop application via screenshots — click, type, scroll, screenshot again, decide next move, without one round trip per single action like the earlier version required.
Browser use tool (GA Aug 20, 2026)Web pages via their actual DOM structure, not just pixels — acts on a named field or button, observes the page's new state, continues.

Different targets — code, a desktop app, a webpage — same four-step architecture underneath all three.

6. What can still go wrong

The loop is powerful precisely because it removes a human checkpoint between steps — which is also where the risk concentrates:

  • Compounding errors. A wrong decision early in the loop doesn't just waste one step — every downstream tool call inherits it, and the agent may confidently keep building on a bad premise.
  • Cost and runaway loops. More passes through the loop means more tokens and more tool calls; a poorly bounded goal can spin far longer (and cost far more) than a human would expect.
  • Tool trust. An agent that calls tools is only as safe as the tools it's allowed to call — a malicious or compromised tool description can manipulate what the model decides to do next, the exact class of problem the MCP ecosystem is still working through in production.

None of this is a reason to avoid agents — it's why every serious agent deployment in 2026 pairs the loop with guardrails: scoped permissions, spend/step limits, and a human approval point for anything irreversible.

O que realmente faz de algo um "agente de IA"

A palavra "agente" foi colada em todo produto de IA neste ano, mas por baixo do marketing existe uma única diferença arquitetural real entre um chatbot e um agente: um loop. Aqui está o que tem dentro dele, e por que quase tudo que a Anthropic lançou em agosto de 2026 — modo automático, computer use, a ferramenta de navegador — é esse mesmo loop com roupas diferentes.

1. Chatbot vs. agente: a única diferença real

Um chatbot recebe sua mensagem, produz uma resposta e para. Cada "turno" é uma ida e volta: você escreve, ele responde, a conversa espera por você de novo. Nada acontece no meio além do modelo gerando tokens.

Um agente é o mesmo modelo por baixo, mas ligado a um loop que não precisa de você entre os passos. Dê a ele um objetivo — "encontre os três voos mais baratos pra sexta-feira que vem e reserve o melhor" — e ele pode buscar, ler resultados, comparar, perceber que falta informação, buscar de novo, e só voltar pra você quando o objetivo estiver realmente concluído (ou quando precisar de uma decisão que só você pode tomar, tipo um número de cartão de crédito).

Essa é a distinção inteira. Não é um modelo maior, não é mais "inteligência" no sentido abstrato — é uma estrutura de controle diferente, envolvendo o mesmo tipo de modelo que dá vida a um chatbot.

2. O loop: perceber, decidir, agir, observar

Todo agente, independente de fornecedor ou framework, roda alguma versão do mesmo ciclo de quatro passos:

  • Perceber — ler o estado atual: o objetivo do usuário, uma captura de tela, um arquivo, uma linha de banco de dados, o resultado da última ação.
  • Decidir — o modelo raciocina sobre o que fazer a seguir, dado o objetivo e o que acabou de perceber. Esse é o passo que as pessoas chamam de "loop agêntico" ou "ciclo de raciocínio-ação" — é literalmente o modelo escolhendo o próximo movimento.
  • Agir — o modelo chama uma ferramenta: rodar uma busca, clicar num botão, executar código, escrever um arquivo, consultar um banco.
  • Observar — o resultado dessa ação vira nova entrada, e o loop volta pro passo 1.

Um chatbot roda esse loop uma vez e imprime texto. Um agente roda quantas vezes o objetivo exigir — às vezes duas, às vezes quarenta — revisando o plano a cada passagem com base no que de fato aconteceu, não só no que ele esperava que acontecesse.

Exemplo resolvido

Objetivo: "Resuma o artigo mais citado sobre memória de agentes deste ano." O agente raciocina que precisa de uma ferramenta de busca, chama ela com uma query, recebe 15 resultados com contagem de citações, escolhe o mais citado, chama uma ferramenta de recuperação de documento pra pegar o resumo, decide que já tem contexto suficiente, e escreve o resumo. Quatro passagens de loop, três chamadas de ferramenta, zero intervenção humana depois do objetivo inicial.

3. Por que uso de ferramentas é o ingrediente-chave

Nada disso funciona sem uma forma padronizada do modelo chamar ferramentas. Na prática isso significa: uma ferramenta é definida com um nome, uma descrição e um schema pros seus parâmetros — o modelo não precisa de código sob medida pra cada ferramenta, só precisa ver o schema e decidir quando usá-la.

Essa é exatamente a lacuna que o Model Context Protocol (MCP) foi criado pra fechar — padronizando como um agente descobre e chama ferramentas e fontes de dados, em vez de cada app escrever código de integração sob medida pra cada modelo. É por isso que a adoção do MCP explodiu ao longo de 2026 junto com o boom de agentes: mais agentes precisando de ferramentas significa mais demanda por uma forma compartilhada de plugar ferramentas.

As próprias ferramentas de computer use e browser use da Anthropic, que ficaram disponíveis de forma geral na Claude Platform em 20 de agosto de 2026, são uma expressão direta dessa ideia levada adiante: em vez do modelo só chamar ferramentas estreitas e feitas sob medida, ele consegue agir sobre software que não tem API nenhuma — clicando, digitando e rolando uma captura de tela do jeito que uma pessoa faria, ou lendo a estrutura real de uma página web e agindo sobre um campo ou botão específico em vez de uma coordenada de pixel.

4. Um agente só vs. orquestração multi-agente

Tarefas simples cabem dentro de um agente só rodando um loop. Mas quando um objetivo tem sub-partes genuinamente independentes — pesquisar uma coisa enquanto rascunha outra, ou verificar uma afirmação enquanto um passo separado continua trabalhando — um loop único vira um gargalo: tudo fica serializado numa única linha de raciocínio.

O padrão que virou comum em meados de 2026 é a orquestração multi-agente: um agente líder quebra o objetivo em sub-tarefas e entrega cada uma a um sub-agente especializado (um "pesquisador", um "programador", um "verificador"), depois junta as saídas. Isso não é só paralelismo por velocidade — também isola o contexto, então a exploração barulhenta de um sub-agente não polui o raciocínio de outro.

Trade-off pra ter em mente: configurações multi-agente custam mais (cada sub-agente consome seus próprios tokens) e adicionam overhead de coordenação (alguém tem que reconciliar saídas divergentes dos sub-agentes). Valem a pena quando as sub-tarefas são genuinamente independentes — não como padrão pra tudo.

5. Onde isso aparece agora, concretamente

Não precisa de um exemplo exótico — três coisas que a Anthropic lançou ou mudou nas últimas semanas são esse mesmo loop em produção, em escopos diferentes:

ProdutoSobre o que o loop age
Modo automático do Claude Code (padrão desde 14/08/2026)Arquivos e comandos de shell num codebase — o loop lê código, decide o que mudar, edita/roda comandos, observa o resultado (testes passam ou falham), repete.
Ferramenta computer use (GA em 20/08/2026)Qualquer aplicativo desktop via capturas de tela — clica, digita, rola, captura de novo, decide o próximo movimento, sem uma ida-e-volta por ação única como a versão anterior exigia.
Ferramenta browser use (GA em 20/08/2026)Páginas web via sua estrutura real de DOM, não só pixels — age sobre um campo ou botão nomeado, observa o novo estado da página, continua.

Alvos diferentes — código, um app desktop, uma página web — a mesma arquitetura de quatro passos por baixo dos três.

6. O que ainda pode dar errado

O loop é poderoso justamente porque remove um checkpoint humano entre os passos — que é também onde o risco se concentra:

  • Erros que se acumulam. Uma decisão errada no início do loop não desperdiça só um passo — toda chamada de ferramenta seguinte herda esse erro, e o agente pode continuar construindo com confiança sobre uma premissa ruim.
  • Custo e loops descontrolados. Mais passagens pelo loop significam mais tokens e mais chamadas de ferramenta; um objetivo mal delimitado pode rodar bem mais tempo (e custar bem mais) do que um humano esperaria.
  • Confiança na ferramenta. Um agente que chama ferramentas só é tão seguro quanto as ferramentas que ele tem permissão de chamar — uma descrição de ferramenta maliciosa ou comprometida pode manipular o que o modelo decide fazer a seguir, exatamente a classe de problema que o ecossistema MCP ainda está resolvendo em produção.

Nada disso é motivo pra evitar agentes — é por isso que todo deployment sério de agente em 2026 combina o loop com salvaguardas: permissões delimitadas, limites de gasto/passos, e um ponto de aprovação humana pra qualquer coisa irreversível.
