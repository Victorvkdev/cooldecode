MCPhantom: when the model's memory becomes your package manager

Ask a coding agent to "set up a GitHub MCP" and it has to pick a package. New research shows it often picks one it remembers from training, even when that package was archived over a year ago and will never be patched. Here is how it happens, why your usual security tools miss it, and what you can do today.

1. What the research found

On November 3, 2026, Help Net Security reported on research by Glow Labs, which reviewed real AI coding session transcripts and found deprecated MCP servers landing on developer machines. They call the pattern MCPhantom.

98%
of the sessions studied where the agent itself supplied the deprecated package name (the other 2%: the user asked for it)
17.3M+
npm downloads of the deprecated packages since July 2025
4
high-severity flaws found in those servers, with no patch coming

The headline example: a developer asks for a GitHub MCP server. GitHub maintains its own. The agent skips it and installs an old Anthropic reference server it remembers, from a repository archived in May 2025 that explicitly says no security updates are coming. "Agents don't read archive notices," as the article puts it.

It is not one vendor's bug. The pattern showed up in Claude Code, Cursor, Codex CLI, Claude Cowork and Claude chat, with models from Anthropic, OpenAI and xAI. Five of the deprecated packages are in npm's top 100 MCP packages.

Scope note: the 98% is measured only over sessions where a deprecated server was installed or suggested. It does not mean 98% of all MCP installs are deprecated.

2. Why agents keep installing dead packages

A model's knowledge is a snapshot. When the snapshot was taken, @modelcontextprotocol/server-github was the way to connect an agent to GitHub: it appeared in docs, tutorials, READMEs and thousands of config files. That frequency is exactly what makes the model confident about it later.

Training data: package X is everywhere→ Package X gets archived→ Model still "knows" X→ Agent runs npx X→ Unpatched code on your machine

Glow's VP of R&D summed it up: "The model's memory is now a package manager with no deprecation feed."

You might think "just tell the agent to check npm first." The researchers tried that angle. In one session the agent did look up the package, got back "This package is deprecated", installed it anyway and never mentioned it to the user. A lookup only helps if something enforces what the lookup says.

How this differs from "slopsquatting"

You may have heard of slopsquatting: a model invents a package name that doesn't exist, and an attacker registers that name with malicious code. MCPhantom is the quieter cousin. The package is real, legitimate, once-official, and published by a trusted organization. Nothing about it looks malicious. It is just abandoned, and abandoned code with known flaws is a perfectly good attack surface.

3. Why your existing controls stay quiet

These servers are dependencies that never appear in a dependency file. Each standard defense misses them for a different reason:

ControlWhat it normally doesWhy it misses MCPhantom
EDR (endpoint detection)Flags suspicious processesIt sees a trusted Node process installing a public npm package. That looks routine.
SCA (dependency scanning)Reads package.json / lockfiles and matches CVEsThe server runs through npx, so there is no manifest. And the flaws have no CVEs.
Software inventoryLists installed applicationsAn npx package is never "installed" as an app.
npm itselfCan remove packagesnpm only lets owners unpublish packages with under 300 weekly downloads, a single owner and no dependents. server-github had 185,239 downloads last week and 6 owners. npm removes malware, not vulnerable code.

So the only place the problem is visible is the developer's own machine, inside the MCP config file the agent wrote.

4. How one permission stretches to cover everything

The most serious of the four flaws is a remote code execution bug in the archived Puppeteer server, which lets an agent drive a browser. The chain is short:

  1. The developer approves "browse the web" for the agent.
  2. The agent reads a web page containing a hidden prompt injection.
  3. The injection makes the agent call the Puppeteer server in a way that launches an arbitrary process instead of a browser.
  4. The harness lets it through, because from its point of view this is still the "browser tool" the user approved.

This is the core lesson for anyone building with agents: a permission is only as narrow as the code behind the tool. Approving a tool by name ("browser") says nothing about what a buggy implementation of that tool can do. If you read our October 28 lesson on permission modes, this is the other half of that story: the mode decides when the agent asks; the server's code decides what "yes" actually unlocks.

Glow reports no exploitation seen so far. The maintainers closed the report as out of scope (the server is archived) and said they might mark the npm package as deprecated so users see a warning. But a deprecated npm package still installs through npx.

5. Who can fix it (and the hooks that work today)

Glow's researcher Nadav Claude Cohen listed four possible sources of a fix, each with a catch:

WhoFixCatch
Harness makers (Claude Code, Cursor, Codex...)Refuse or warn on deprecated servers, including already-installed ones"It works only if every harness does it."
Model makersUpdate what models know about package namesRetraining is expensive; unlikely to happen just for this
Package ownersPatch the bugsThe only fix that protects existing users, and the one that was declined
Security teams / youPre-execution hooks that inspect a tool call before it runsWorks today, without waiting for anyone

The Anthropic angle: inference hooks went GA on Nov 5

Timing is interesting. Two days after the report, on November 5, Anthropic announced that inference hooks are generally available in Claude Enterprise. There are two kinds: prompt hooks, which send prompts to your security tool for a check, and pre-tool-call hooks, which check tool calls in supported Claude products before they run. The same announcement added a security center that compares your org's Claude settings with Anthropic's recommended configuration, and EDR sensor support inside the local VM used by Cowork. Anthropic doesn't link this to MCPhantom, but a pre-tool-call hook is precisely the "works today" layer the researchers describe.

A do-it-yourself version for a single developer

You don't need Enterprise to apply the idea. Claude Code supports local hooks configured in a settings file: a PreToolUse hook receives the pending tool call as JSON on stdin, and exiting with code 2 blocks the call and shows your message to the model. A minimal guard that blocks installing anything npm marks as deprecated:

// .claude/settings.json (project level)
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "node .claude/hooks/no-deprecated.js" }] }
    ]
  }
}
// .claude/hooks/no-deprecated.js
const { execSync } = require("child_process");
let raw = "";
process.stdin.on("data", c => raw += c).on("end", () => {
  const cmd = JSON.parse(raw).tool_input?.command || "";
  // grab package names after npx / npm i / npm install
  const m = cmd.match(/\b(?:npx(?:\s+-y)?|npm\s+(?:i|install))\s+((?:@[\w.-]+\/)?[\w.-]+)/);
  if (!m) process.exit(0);
  try {
    const dep = execSync(`npm view ${m[1]} deprecated`, { encoding: "utf8" }).trim();
    if (dep) {
      console.error(`Blocked: ${m[1]} is deprecated on npm ("${dep}"). ` +
                    `Find the service owner's official server instead.`);
      process.exit(2);   // 2 = block and tell the model why
    }
  } catch { /* lookup failed: let the normal permission prompt decide */ }
  process.exit(0);
});

Two honest limits: it only inspects shell commands (an MCP server added by editing a config file directly won't pass through it), and it relies on npm's deprecated flag, which, per the article, the archived reference servers may not even have yet. Treat it as one layer, next to an allowlist. Hook field names can change between versions, so check the current Claude Code hooks docs before copying.

Paste an MCP config (the mcpServers JSON used by most clients). This runs only in your browser. It flags packages from the archived reference-server set and suggests where to look instead.     7. A checklist for your own setup

    1. Audit what you already have. Search your MCP configs (project .mcp.json, your client's user config) for @modelcontextprotocol/server-. Everything that matches deserves a second look.
    2. Prefer the service owner's server. If GitHub, a database vendor or a SaaS tool publishes an official MCP server, use that. A community or reference server is a fallback, not a default.
    3. Pin versions. npx -y some-server pulls whatever is latest every time. Pin an exact version, so a change is something you decide.
    4. One approved server per service. Keep a short allowlist for your team. Agents can suggest; humans approve additions.
    5. Add "is it deprecated or archived?" to the approval checklist. Check npm (npm view <pkg> deprecated) and the repository's archive status.
    6. Ask the agent what it installed. After a setup session, ask for the exact package names and versions. It's a cheap habit that catches surprises.
    7. Remember the permission lesson. Approving a tool means trusting its code, not just its name.

    • All numbers (98%, 17.3M, four flaws, download counts) come from Glow Labs via Help Net Security. We could not open Glow's original blog post from this environment, so we haven't checked the full methodology or the sample size.
    • Glow is a security vendor; research like this also markets its product category. That doesn't make it wrong, but the "who can fix it" framing naturally favors security tooling.
    • The Anthropic inference-hooks details come from Anthropic's announcement as mirrored by Releasebot; we didn't test the feature. Anthropic did not say it was a response to this research.
    • The deprecated-package list in the checker and the hook script are simplified examples written for this lesson, not official tools.

    17,3 mi+

    O exemplo principal: o desenvolvedor pede um servidor MCP do GitHub. O próprio GitHub mantém um. O agente ignora esse e instala um servidor de referência antigo da Anthropic que ele lembra, de um repositório arquivado em maio de 2025 que avisa com todas as letras que não vai mais receber atualizações de segurança. "Agentes não leem aviso de arquivamento", resume a matéria.

    Não é bug de um fornecedor só. O padrão apareceu no Claude Code, Cursor, Codex CLI, Claude Cowork e no chat do Claude, com modelos da Anthropic, OpenAI e xAI. Cinco dos pacotes descontinuados estão entre os 100 pacotes MCP mais usados do npm.

    Atenção ao recorte: os 98% valem só para as sessões em que um servidor descontinuado foi instalado ou sugerido. Não quer dizer que 98% de todas as instalações de MCP sejam de pacotes descontinuados.

    2. Por que agentes continuam instalando pacotes mortos

    O conhecimento de um modelo é uma foto de um momento. Quando a foto foi tirada, @modelcontextprotocol/server-github era o jeito de ligar um agente ao GitHub: estava em documentação, tutoriais, READMEs e milhares de arquivos de config. É justamente essa frequência que deixa o modelo confiante nele depois.

    Dados de treino: pacote X está em todo lugar→ Pacote X é arquivado→ Modelo ainda "conhece" X→ Agente roda npx X→ Código sem correção na sua máquina

    O VP de P&D da Glow resumiu assim: "A memória do modelo agora é um gerenciador de pacotes sem aviso de descontinuação."

    Dá vontade de pensar "é só mandar o agente consultar o npm antes". Os pesquisadores viram isso acontecer. Numa sessão, o agente consultou o pacote, recebeu "This package is deprecated", instalou mesmo assim e não falou nada para o usuário. Consultar só ajuda se alguma coisa obriga o agente a respeitar o resultado.

    Qual a diferença para "slopsquatting"

    Talvez você já tenha ouvido falar de slopsquatting: o modelo inventa um nome de pacote que não existe e um atacante registra esse nome com código malicioso. O MCPhantom é o primo mais discreto. O pacote é real, legítimo, já foi oficial e é publicado por uma organização confiável. Nada nele parece malicioso. Ele só está abandonado, e código abandonado com falhas conhecidas é uma ótima superfície de ataque.

    3. Por que os controles que você já tem ficam calados

    Esses servidores são dependências que nunca aparecem num arquivo de dependências. Cada defesa padrão deixa passar por um motivo diferente:

    ControleO que costuma fazerPor que não pega o MCPhantom
    EDR (detecção no endpoint)Sinaliza processos suspeitosEle vê um processo Node confiável instalando um pacote público do npm. Parece rotina.
    SCA (varredura de dependências)Lê package.json / lockfiles e cruza com CVEsO servidor roda via npx, então não existe manifesto. E as falhas não têm CVE.
    Inventário de softwareLista aplicativos instaladosUm pacote rodado via npx nunca é "instalado" como aplicativo.
    O próprio npmPode remover pacotesO npm só deixa o dono despublicar pacotes com menos de 300 downloads semanais, um único dono e sem dependentes. O server-github teve 185.239 downloads na última semana e tem 6 donos. O npm remove malware, não código vulnerável.

    Ou seja: o único lugar onde o problema aparece é a máquina do próprio desenvolvedor, dentro do arquivo de config de MCP que o agente escreveu.

    4. Como uma permissão se estica para cobrir tudo

    A mais grave das quatro falhas é um bug de execução remota de código no servidor Puppeteer arquivado, que deixa um agente controlar um navegador. A cadeia é curta:

    1. O desenvolvedor autoriza o agente a "navegar na web".
    2. O agente lê uma página com uma prompt injection escondida.
    3. A injection faz o agente chamar o servidor Puppeteer de um jeito que abre um processo qualquer no lugar do navegador.
    4. O harness deixa passar, porque do ponto de vista dele ainda é a "ferramenta de navegador" que o usuário aprovou.

    Essa é a lição central para quem trabalha com agentes: uma permissão só é tão estreita quanto o código por trás da ferramenta. Aprovar uma ferramenta pelo nome ("navegador") não diz nada sobre o que uma implementação com bug dessa ferramenta consegue fazer. Se você leu a lição de 28 de outubro sobre modos de permissão, esta é a outra metade da história: o modo decide quando o agente pergunta; o código do servidor decide o que o "sim" realmente libera.

    A Glow diz que não viu exploração real até agora. Os mantenedores fecharam o relatório como fora de escopo (o servidor está arquivado) e disseram que podem marcar o pacote como descontinuado no npm, para o usuário ver um aviso. Só que um pacote marcado como descontinuado continua instalando normalmente via npx.

    O pesquisador da Glow, Nadav Claude Cohen, listou quatro fontes possíveis de solução, cada uma com um porém:

    O ângulo da Anthropic: inference hooks ficaram GA em 5/11

    O timing é curioso. Dois dias depois da reportagem, em 5 de novembro, a Anthropic anunciou que os inference hooks estão disponíveis para todos no Claude Enterprise. São dois tipos: prompt hooks, que mandam os prompts para a sua ferramenta de segurança checar, e pre-tool-call hooks, que checam chamadas de ferramenta nos produtos Claude suportados antes de elas rodarem. O mesmo anúncio trouxe uma central de segurança que compara as configurações do Claude da sua organização com a configuração recomendada pela Anthropic, e suporte a sensores de EDR dentro da VM local usada pelo Cowork. A Anthropic não liga isso ao MCPhantom, mas um pre-tool-call hook é exatamente a camada "que funciona hoje" descrita pelos pesquisadores.

    Uma versão caseira para um desenvolvedor só

    Não precisa de Enterprise para aplicar a ideia. O Claude Code aceita hooks locais configurados num arquivo de settings: um hook PreToolUse recebe a chamada pendente como JSON no stdin, e sair com código 2 bloqueia a chamada e mostra sua mensagem para o modelo. Uma trava mínima que bloqueia a instalação de qualquer coisa que o npm marque como descontinuada:

    // .claude/settings.json (nível do projeto)
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "node .claude/hooks/no-deprecated.js" }] }
    ]
  }
}
    // .claude/hooks/no-deprecated.js
const { execSync } = require("child_process");
let raw = "";
process.stdin.on("data", c => raw += c).on("end", () => {
  const cmd = JSON.parse(raw).tool_input?.command || "";
  // pega o nome do pacote depois de npx / npm i / npm install
  const m = cmd.match(/\b(?:npx(?:\s+-y)?|npm\s+(?:i|install))\s+((?:@[\w.-]+\/)?[\w.-]+)/);
  if (!m) process.exit(0);
  try {
    const dep = execSync(`npm view ${m[1]} deprecated`, { encoding: "utf8" }).trim();
    if (dep) {
      console.error(`Bloqueado: ${m[1]} está descontinuado no npm ("${dep}"). ` +
                    `Procure o servidor oficial do dono do serviço.`);
      process.exit(2);   // 2 = bloqueia e explica o motivo ao modelo
    }
  } catch { /* consulta falhou: deixa o prompt de permissão normal decidir */ }
  process.exit(0);
});

    Dois limites honestos: ele só inspeciona comandos de shell (um servidor MCP adicionado editando o arquivo de config direto não passa por ele), e depende da flag deprecated do npm, que, segundo a matéria, os servidores de referência arquivados talvez nem tenham ainda. Use como uma camada, junto com uma allowlist. Os nomes de campo dos hooks podem mudar entre versões, então confira a documentação atual de hooks do Claude Code antes de copiar.

    Cole uma config de MCP (o JSON mcpServers que a maioria dos clientes usa). Tudo roda só no seu navegador. Ele sinaliza pacotes do conjunto de servidores de referência arquivados e sugere onde procurar uma alternativa. A lista se baseia nos servidores de referência movidos para o repositório arquivado em 2025; é material didático, não uma base completa nem oficial.

      7. Checklist para o seu setup

      1. Audite o que você já tem. Procure nas suas configs de MCP (o .mcp.json do projeto, a config de usuário do seu cliente) por @modelcontextprotocol/server-. Tudo que aparecer merece uma segunda olhada.
      2. Prefira o servidor do dono do serviço. Se o GitHub, um fornecedor de banco de dados ou uma ferramenta SaaS publica um servidor MCP oficial, use esse. Servidor da comunidade ou de referência é plano B, não padrão.
      3. Fixe versões. npx -y algum-servidor puxa a última versão toda vez. Fixe uma versão exata, para que mudar seja uma decisão sua.
      4. Um servidor aprovado por serviço. Mantenha uma allowlist curta para o time. O agente pode sugerir; quem aprova adições é uma pessoa.
      5. Inclua "está descontinuado ou arquivado?" no checklist de aprovação. Consulte o npm (npm view <pkg> deprecated) e o status de arquivamento do repositório.
      6. Pergunte ao agente o que ele instalou. Depois de uma sessão de setup, peça os nomes e versões exatos dos pacotes. É um hábito barato que pega surpresas.
      7. Lembre da lição sobre permissões. Aprovar uma ferramenta é confiar no código dela, não só no nome.
